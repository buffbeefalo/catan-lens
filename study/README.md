# Catan Lens human studies

> **Status, 12 October 2026: no reviews and no participants yet.** Nobody has reviewed these positions and nobody has taken part in a study session. Recruitment and results are outstanding. Nothing in this folder is evidence for or against either Catan Lens policy, and the files in `demo/` are made up by a script.

This folder holds the materials for two separate studies of Catan Lens's opening advice. Both run from files on one computer, with no server, no account, no tracking and no network.

| Study | Question | Materials |
|---|---|---|
| A. Expert review | Do strong players who cannot see what Catan Lens chose pick the same opening corners as its two policies? | `review.html`, `analyze.mjs`, `positions-2026-10-12.json` |
| B. Usability and learning | Can players use Catan Lens without help, and do they choose better openings after practising with it than after reading a strategy article for the same time? | `LEARNING-PROTOCOL.md`, `review.html?form=A` (or `B`, `C`) |

The two policies:

- **Classic**: the ranking the app shows (`public/score.js`).
- **Look-ahead**: `public/lookahead.js`, policy `draft-aware-2026-10-12`, which also weighs what the other players are likely to take before your next turn.

Neither policy has been checked against human experts or against human learning. These materials are how that check would be done.

## The positions and how they were chosen

This rule was fixed on 12 October 2026, before any review, and is stored word for word in the positions file. It never looks at what either policy would choose.

1. **Boards.** 4-player base game boards generated by Catan Lens (`public/board.js`, balanced setup) from seeds 9,000,000 to 9,000,023, one position per seed, in seed order. Seeds 9,000,000 to 9,000,999 are reserved for these studies; no benchmark or test uses them.
2. **Seat.** Position k (k = 1 to 24) is seat ((k - 1) mod 4) + 1, so seats run 1, 2, 3, 4, 1, 2 and so on.
3. **Task.** Positions 1 to 4 ask for a first settlement, positions 5 to 8 for a second settlement, and so on, switching every four positions. That gives 12 first and 12 second settlement tasks, three of each for every seat.
4. **Pieces already placed.** Every settlement placed before the task in snake order (seats 1, 2, 3, 4, then 4, 3, 2, 1), copied from the classic projected opening (`simulateDraft` in `public/score.js`) for that board. This fixes the position only; nothing about any policy's next choice is stored.
5. **Learning study forms.** A is P01 to P08, B is P09 to P16, C is P17 to P24. Each form has every seat once for each task.

The file stores every tile, number and harbour, so the positions stay the same even if the board generator changes later. Corners are numbered 1 to 54 on the page and in every file; in Catan Lens code a corner id is its number minus 1.

**Freeze.** Once the first reviewer starts, do not change the positions file. A different set needs a new version name and a new file. If the team wants more positions, extend the same rule to more seeds (P25 from seed 9,000,024 onwards) before any review starts.

**How many positions separate the policies.** With the code at this commit, the two policies choose different corners on 7 of the 24 positions (6 of the 12 first settlement tasks and 1 of the 12 second settlement tasks). This file does not say which ones, so a reviewer who reads it stays blind. A direct comparison between the policies rests on those few positions; see [Limitations](#limitations).

## Study A: the blinded review

### Before the review

- Give each reviewer a code, for example `R01`. Reviewers type only this code; no names or email addresses go into any file. Record their playing experience against the code in `templates/expert-reviewers.csv`.
- Give each reviewer the repository, or at least the `study/` and `public/` folders (the page uses `public/board.js`, `public/geometry.js`, `public/style.css` and `public/icons/icon.svg`).
- Ask reviewers not to use Catan Lens or any other tool while they answer, and not to discuss the positions with each other until everyone has finished.

### Opening the page

- **Firefox:** open `study/review.html` straight from the disk (File, then Open File).
- **Chrome, Edge or Safari:** these block pages opened from a file, and the page says so. Run a local preview from the repository folder, which only this computer can reach:

  ```
  python3 -m http.server 8000 --bind 127.0.0.1
  ```

  then open `http://127.0.0.1:8000/study/review.html`. (`npm start` serves only `public/`, so it cannot show this page.)

### What reviewers do

The page shows one position at a time, in the same order for everyone (P01 to P24), with numbered corners and the pieces already placed. For each position the reviewer:

1. picks the corner they would actually play, by clicking the board or using the list;
2. for a first settlement, may name the second settlement they would aim for;
3. ticks any other corners a strong player could reasonably choose instead;
4. says how sure they are, from 1 (a guess) to 5 (certain), and may add a sentence on why.

Everything works from the keyboard as well as the mouse. The page never shows rankings, scores, explanations or which policy chose what: it loads only the board drawing code, the geometry code and the positions file. `test/study-review.test.js` checks every file the page loads, and that none of them makes a network call.

### Saving and handing in answers

- Answers are kept in the browser as the reviewer goes. If the browser blocks storage, the page says so, and the answers last only while the page stays open.
- **Download my answers** saves a file such as `catan-review-R01-2026-10-20.json`. Each download holds everything answered so far. Nothing is sent anywhere.
- **Clear answers on this device** removes them from that browser.
- Keep real answer files out of git: store them outside the repository, or in `study/responses/`, which `.gitignore` excludes.

## Study A: the analysis

```
node study/analyze.mjs study/responses/*.json
node study/analyze.mjs --json results.json study/responses/*.json
```

Give it one file per reviewer: their latest download. The script:

- works out each policy's choice for every position only when it runs, with the code in the repository at that moment, and prints the SHA-256 hashes of that code so a result can be tied to the exact code;
- reports, for classic, look-ahead and a most-pips baseline (the open corner with the most dots on its number tokens), how often the reviewer's top choice is the policy's choice, how often the reviewer accepts the policy's choice, and whether the policy's choice is in the panel set: every corner accepted by at least half of a position's reviewers, counted when two or more reviewers rated it;
- gives the chance level: how often a corner picked at random from the open ones would match a reviewer's top choice;
- compares first settlement plans: the reviewer's choice and planned second against each policy's choice and projected second;
- measures agreement between reviewers: the share of reviewer pairs with the same top choice, Fleiss' kappa (agreement corrected for chance), and the overlap of accepted corners;
- splits the results by whether the two policies agree, by seat, by first or second settlement task, by reviewer and by position;
- lists every problem it finds in the files (unknown positions, repeated answers, illegal corners) and leaves those entries out rather than counting them;
- refuses to mix synthetic and real files, refuses two files with the same reviewer code, and refuses study B test files.

Agreement with expert reviewers is one source of evidence, not proof that any choice is best. Reviewers can share blind spots, and a policy can be right where reviewers disagree. The report says so at the top, and the JSON file carries the same caveat.

> **Keep the output away from reviewers.** The report lists the corner each policy chooses on every study position, and so does the demonstration run below. Do not run it in front of a reviewer, or share it with anyone who has not finished reviewing.

### Planned comparison

Fixed before any data exist, so the results cannot shape the question:

1. **Reviewers.** At least 5 experienced players (a planning assumption), each answering all 24 positions. With fewer, the panel sets and kappa are unstable.
2. **Reliability first.** Report agreement between reviewers (the pairwise share and Fleiss' kappa on top choices) before any policy comparison. Low agreement means the panel itself is unsure, and agreement with a policy should be read with that in mind.
3. **Primary measure.** On the positions where the two policies choose different corners, the share of reviewer top choices that match each policy, shown next to the most-pips baseline and the chance level.
4. **Secondary measures.** On all 24 positions: top choice agreement, acceptance of each policy's choice, panel set membership, and plan matches on first settlement tasks, split by seat and by task.
5. **Uncertainty.** The script prints counts only, and ratings of the same position or by the same reviewer are not independent. Any reported difference between the policies needs a confidence interval that treats positions as the unit, for example a bootstrap over positions. The script does not compute this yet.

## Study B: usability and learning

See [LEARNING-PROTOCOL.md](LEARNING-PROTOCOL.md). Its unaided tests use the review page in test mode: `review.html?form=A` (or `B`, `C`) shows only that form's 8 positions and asks only for a corner and how sure the participant is. ## Demonstration (synthetic data only)

```
node study/analyze.mjs study/demo/synthetic-reviewer-1.json study/demo/synthetic-reviewer-2.json study/demo/synthetic-reviewer-3.json
node study/demo/make-synthetic.mjs
```

The first command runs the analysis on the demonstration files; the second rebuilds them exactly. The three files in `demo/` are SYNTHETIC: a seeded random process made up every answer, leaning towards corners with more dots. No person reviewed these positions. The files say so in their names, in their contents (`"synthetic": true`, a note, and reviewer codes SYNTHETIC-1 to SYNTHETIC-3) and at the top and bottom of every report made from them. Never copy them next to real answer files; the analysis refuses to mix the two.

## Limitations

- The positions are generated boards (balanced setup, 4 players, base game). Results may not carry over to other setups or player counts.
- Pieces placed before the task come from the classic projection, not from real players, so the positions follow the classic policy's idea of how others play.
- Every reviewer sees the positions in the same order, so tiredness and warming up fall on the same positions for everyone.
- Only 7 of the 24 positions separate the two policies, so a direct comparison between them will be imprecise.
- The panel set counts a corner when at least half of the reviewers accept it; with only two or three reviewers that is a lenient bar.
- Experts can share blind spots. Agreement with them is not proof that a choice is best.
- The review page was checked with browser scripts in Firefox (from a file) and in Chromium and WebKit (local preview) during development. The repository's automated browser suite does not cover it.
